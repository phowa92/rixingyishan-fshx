# 日行一善网站用量优化设计（实施前记录）

实施后的图片体积、测试和查询数据以 [本地验证结果](../../optimization-results-2026-11-17.md) 为准。图片在用户确认 0.2 MB 目标后进一步压缩到 196,322 B，保留完整横向构图；本文下方的 368,006 B 是此前的设计候选值。

## 目的与边界

降低 `fshx` 的 Netlify 流量、请求和函数计算，以及 Supabase 的查询次数、数据库计算和出站量，同时保留现有静态 HTML/CSS/JS、Netlify Functions、Supabase 数据库和 Supabase Auth。名单内容、权限、七日有效期和用户操作保持一致。本轮另将填写页的“＋”添加姓名按钮做成醒目的暖金色实底按钮，尺寸和所在位置不变。

**已确认的实时性选择：**公开名单始终实时读取。`GET /api/records` 不使用 CDN、durable 或浏览器数据缓存；提交或管理员修改、删除成功后，后续公开读取直接查询 Supabase。原先讨论的 30 秒缓存方案已被否决，不实施缓存清除、强制刷新参数或旧数据窗口。这里的“实时”指写入事务成功后的新请求；已在进行中的并发读取可能先于写入完成。

**发布边界：**只在本地或隔离测试环境修改和验证。用户本地测试确认并明确发出部署指令之前，不推送生产分支、不执行 Netlify 部署，也不对生产 Supabase 应用迁移。实际 Netlify Deploy Preview 也是部署；执行它之前同样等待用户明确授权。

## 归属、现状和测量界限

- Netlify 站点 `fshx` 属于 `phowa92` 团队，连接 `phowa92/rixingyishan-fshx` 的 `main`。线上发布提交与本地 `HEAD` 均为 `7692530`；推送 `main` 会触发正式构建，故优化过程不能推送 `main`。
- 本地 `main` 有 7 个已修改文件及未跟踪的 `output/`，主要是尚未发布的提交确认勾选、回向文和排版。优化分支必须保留这些修改，不把 `output/` 混入网站发布物。
- 当前链接的 Supabase 项目为 `rixingyishan-fshx`，位于“日行一善”组织、新加坡区域；项目与 `phowa` 网站数据库分开。项目控制台归属由 CLI 项目元数据确认，不能仅由本地目录名推断登录身份。
- Netlify Free 团队每周期 300 积分；用户截图显示当前团队剩余 278、总消耗 21.6，其中正式部署 15、网页请求约 1、计算 2.2、流量 3.5。分项显示值相加为 21.7 是取整所致。账单数据是 **团队两站合计**，不能当作本站实测或每次登录价格。当前周期在 Netlify UI 显示为 11 月 15 日至 12 月 14 日；账户 API 给出的下次周期起点换算为北京时间 12 月 15 日 16:00。以上都是本次调查时点的数据，不用于承诺未来账单节省。
- 当前测试命令 `npm test`：10/10 通过。公开接口、资源大小的现网样本是只读测量，不代表长期平均或每个地区的 CDN 行为。

### 可复现的初步基线

本地临时基线脚本使用当前函数、同样的模拟 Supabase 分页返回，记录上游请求数、行数、JSON 字节和函数自身处理时间；未引入网络/数据库真实执行时间，也未读取线上姓名。正式实施时把相同数据生成与访问脚本放进仓库，迁移前后同脚本重跑，记录中位数与尾部延迟。

| 合成数据 | 原始行 / 前台结果 | Supabase 请求 | 上游 JSON | 前台 JSON |
| --- | ---: | ---: | ---: | ---: |
| 小数据 | 12 / 8 | 1 | 2,137 B | 288 B |
| 多重复 | 2,400 / 100 | 3 | 427,203 B | 1,486 B |
| 结果超千条 | 2,200 / 2,200 | 3 | 391,603 B | 28,787 B |

可见大量重复时数据库出站与最终公开结果相差很大；真实 SQL 执行耗时、索引计划、线上 Supabase 出站和本站单独账单仍缺少直接指标。Supabase CLI 远程迁移查询在初始化连接时未完成，因此本阶段没有把线上数据库指标当作已取得。

### 预计变化与验收目标

下表把**现有实测或同脚本模拟基线**与**实施候选/目标**分开。图片目标是文件体积；Supabase 字节目标是函数从数据库收到的 JSON，均不能直接换算为账单积分。最终值必须在相同数据、相同操作下复测。

| 场景与所省资源 | 目前基线 | 优化目标 / 预计变化 | 名单时效与限制 |
| --- | --- | --- | --- |
| 首次首页海景图：Netlify 静态出站 | 线上 PNG 实传 1,828,721 B | 保留完整 1672×941 横图，仅压缩：JPEG 质量 88 为 368,006 B，约少 80%，是画质优先的推荐候选；质量 80 为 294,979 B，约少 84%。竖屏和横屏均用同一完整图片。 | 待用户查看原图与候选的同视口页面截图后定稿；不制作手机专用裁剪图。 |

| 公开名单，大量同名：Supabase 请求和出站 | 模拟 2,400 条原始、100 条显示，3 次读取、427,203 B 上游 JSON | 目标 1 次 RPC、约 2–10 KB 上游 JSON，即请求少约 67%、响应体少约 98%–99%；SQL 计算量须另测。 | 公开响应仍为原有约 1,486 B JSON，页面名单和去重顺序不变。 |
| 公开名单，最终结果超千条：Supabase 请求和出站 | 模拟 2,200 条原始/显示，3 次读取、391,603 B 上游 JSON | 目标 1 次 RPC、约 29–50 KB 上游 JSON，即请求少约 67%、响应体少约 87%–93%；确保结果不截断。 | 公开响应仍为原有约 28,787 B JSON，结果完整且实时。 |
| 公开名单：Netlify Function 次数 | 每次打开 1 次 | 保持每次打开 1 次，**预计减少 0 次**；若 RPC 使函数执行更短，计算积分才可能下降。 | 无 30 秒旧名单窗口；不缓存名单数据。 |
| 后台手动登录后只查看名单：Netlify / Supabase 请求 | 约 5 次函数、14 次 Auth/数据库请求（当前还自动加载账户和日志） | 登录返回账户、账户及日志按需加载后，目标约 2 次函数、6 次上游请求；若打开账户或日志，仍会按需查询。 | 权限每次受保护请求都核实；首次展开区域可能稍等加载。 |
| 后台姓名搜索连续输入：Netlify / Supabase 请求 | 输入 5 个字符通常触发 5 次函数、约 15 次上游请求 | 停顿时间短于防抖阈值的一串输入，目标 1 次函数、约 3 次上游请求；缓慢输入仍可能多次查询。 | 搜索结果延迟约 250–350 毫秒，具体阈值以本地交互验证。 |
| 提交、编辑、删除、导出、每日清理 | 批量提交 1 次写入；后台保留原始行；CSV 全量；清理 1 次 RPC/日 | 优先不改次数和数据语义；仅减少操作前后的冗余读取。 | 提交成功后的下一次公开读取可见新名单。 |

**账单预测边界：**团队截图的 21.6 积分包含两站，无法据此计算 `fshx` 每月会省多少积分；正式部署本身仍按账单计费，已有积分不返还。图片缩小预计主要影响 Netlify 带宽，登录/搜索减少请求预计影响 Netlify 请求与函数计算，公开名单聚合主要影响 Supabase 出站与往返。数据库聚合可能增加 SQL 计算；只有真实 Postgres 的执行计划、耗时和相近访问量下的站点/团队账单才能判断净收益。

## 考虑过的路线

1. **只优化图片和资源缓存。**实现与回退最简单，降低静态流量及重复请求；名单仍全量分页，Supabase 大量原始记录出站与后台请求不变。
2. **实时名单 + 数据库聚合 + 静态优化 + 有证据的后台减费（选定）。**名单每次仍查最新数据库，但数据库先按原规则去重并返回单个 JSON 值，避免超过 1000 行的 PostgREST 返回上限和大量原始行出站。图片压缩、静态资源长期复用；后台消除已证明的重复会话/加载请求。实现复杂度中等，名单更新时效不变。
3. **额外加入 30 秒 CDN/durable 缓存。**可进一步减少公开函数和数据库读取，但普通访客可能短暂看到旧名单，缓存清除还受传播与频率限制。用户明确拒绝，排除。

## 选定设计

### 1. Supabase 实时聚合

新增只授权 `service_role` 的数据库函数，接收调用方传入的北京时间七日边界 `timestamptz`。函数用窗口排序按 `group_key`、有效子类目、`name_key` 取最新一条；“最新”按 `submitted_at DESC,id DESC` 判定。历史祈福空子类目按 `personal` 归类；病患保持空子类目。最终结果再按同样的时间、ID 降序排列，保留每组姓名顺序。

RPC 返回**单个 JSON 值**而非 `SETOF` 行，避免 `max_rows=1000` 截断，且只含前台需要的类别、子类目和姓名。Netlify Function 继续生成现有 `{groups,asOf}` 响应，不改变页面接口。超过 1000 原始行与超过 1000 去重结果均通过自动化测试验证。后台仍直接查 `records` 原始表，独立提交和重复姓名完全保留。

数据库函数使用明确的 `SECURITY INVOKER`、固定 `search_path`、完整 schema 限定、`REVOKE`/`GRANT`，不改公开 RLS；迁移仅增加函数，先兼容当前线上版本。现有 `records_submitted_at_idx` 和 `records_visible_dedupe_idx` 先复用。只有在同数据集的 `EXPLAIN (ANALYZE, BUFFERS)` 证明必要时才增加索引，并记录它给写入与存储带来的代价。用同一批含同时间戳、历史空子类目、大量重复的数据比较旧 JS 与新 SQL 的完整输出、请求数、SQL 时间和出站字节；若 SQL 计算成本明显劣于旧方案，保留旧实现并说明原因，不为节省网络而牺牲数据库稳定性。

### 2. 公开名单始终实时

`GET /api/records` 的成功、错误及无效请求均返回 `Cache-Control: no-store`，并显式禁止 Netlify CDN 缓存；不使用 `stale-while-revalidate`。提交和后台新增、修改、删除在 Supabase 写入成功后返回成功；下一次公开 GET 直接查询。无需缓存清除，因此不存在“写入成功但清除失败”导致误报提交失败的问题；并发提交由数据库各自提交，后续查询按确定性顺序读到已提交数据。跨午夜时每次查询重新计算北京时间边界，不依赖定时清理已执行。预览与生产使用不同数据库凭据；未配置预览库时预览函数拒绝访问，避免误碰生产数据。

这里不会降低重复打开名单产生的 **Netlify Function 次数**。预期收益来自函数内部更少的 Supabase 往返/出站及可能更短的执行时间。真实的 Netlify 积分效果必须在相近访问量下另行观察。

### 3. 图片、浏览器缓存及“＋”按钮

已从现有 1672×941 PNG 制作**独立预览样张**，未替换网站图片：保持全部画面、尺寸不变的 JPEG 质量 88 为 368,006 B，质量 80 为 294,979 B。使用 Chrome 在相同 390×844 手机竖屏、844×390 手机横屏和 1440×900 桌面视口渲染原图与候选。先前尝试缩小整张横图或制作竖版裁剪图，用户已明确不采用；手机也必须使用未裁剪的完整横图，只做压缩。当前推荐质量 88 的单一图片供所有屏幕使用，质量 80 是进一步压缩的备选。样张在 `output/previews/`，用户看过并选定后才把图片接入网站。最终还需检查真实 iPhone/Android 屏幕与网络传输；不以 100 KB 为硬性目标。现有 CSS 的 `background-size: cover` 在竖屏会按容器比例显示画面中央部分，但图片文件本身不会被预先裁剪；横屏仍可显示更宽的海景。

建立统一的内容哈希资源地址：一次构建把 HTML、CSS、JS、图片复制到发布目录并写入同一版本清单，所有页面与 CSS 内引用由构建脚本一致地替换。哈希资源允许浏览器长期缓存；HTML 保持及时检查新版本。先用浏览器和 `curl` 验证新版地址更新、旧版缓存复用、重复访问的传输量与请求数。CSS/JS 现网 gzip 仅约 6–7 KB，先不拆包，除非测量显示明确收益。

填写页现有“＋”按钮改为暖金实底、白色加号，与灰白的“－”区别明显；保留触控尺寸、键盘焦点和禁用态，验证窄屏及字体放大时不挤压姓名输入框。

### 4. 后台及清理

先通过浏览器请求日志与模拟上游计数确认登录和搜索负载。优先让成功登录响应直接返回已授权账户信息，免去紧接着的重复会话请求；随后把账户/清理日志改为只在对应区域展开或进入可见范围时加载，并在姓名搜索输入上加入短防抖，减少连续键入触发的请求。每个后台受保护接口仍执行 Supabase Auth 和授权表校验；任何合并读取都不得跳过权限检查。

精确计数用于正确翻页，暂保留；批量删除按 100 ID 分批及原始记录 CSV 导出暂保留，避免误删或漏导；每日清理保持一次 RPC。若测量显示这些项目的开销高于上述重点，再单独提出修改和等价测试。

## 工作区、测试与发布顺序

使用 Superpowers `using-git-worktrees` 检查并建立隔离分支；从当前 `main` 的已发布提交建立工作区，安全地承接那 7 个未提交文件的差异，先验证现有 10 项测试与本地预览，再进行 TDD。`output/` 不随代码复制或发布。开发只在本地分支；不得推送会触发生产部署的 `main`。

每个新逻辑先写行为测试并看到失败，再实现通过。测试覆盖：同名独立保存、前台去重、时间戳相同按 ID 排序、祈福历史空子类目、北京时间边界、>1000 原始及结果、后台权限/导出、静态资源哈希、图片表现和按钮可用性。通过真实 Postgres 兼容环境运行 SQL 结果与执行计划；若本机缺数据库运行时，先建立本地测试依赖，不直接在生产库试错。遇到失败按 `systematic-debugging` 找根因，并按选定执行工作流审查。

迁移先在隔离库验证，确认旧线上函数仍能工作；正式阶段须在用户明确授权后，先应用兼容的数据库迁移并核对，再一次发布依赖它的网站版本。发布异常以恢复旧站为先；因新增函数不改变旧表，网站可先回退旧代码。实际 Netlify Preview 的静态缓存行为需验证，但任何 Preview 部署也要先取得明确部署指令；其函数不得使用生产 Supabase 环境变量。

最终交付按同数据同脚本给出前后 Supabase 请求/行数/出站、函数调用/耗时、资源传输/缓存命中；用每 1000 次可比操作归一化。资源体积、函数调用与实际账单分开写。历史已扣积分不变，未来账单收益只在访问量相近的周期验证。
