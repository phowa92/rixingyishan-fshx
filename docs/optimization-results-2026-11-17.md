## 路径与已完成改动

| 操作 | 原路径 | 本地改动后的路径 |
| --- | --- | --- |
| 首次首页 | HTML + CSS + JS + 1,828,721 B PNG；0 函数、0 数据库 | HTML + 哈希 CSS/JS + 196,322 B 同尺寸完整横向 JPEG；0 函数、0 数据库 |
| 重复首页 / 跨页面 | HTML 与静态资源需验证更新 | HTML 每次检查新版；同内容的哈希 CSS/JS/图片长期复用。本地 Chrome 连续访问时这三个资源命中浏览器缓存 |
| 公开名单 | 1 次 Netlify Function；按 1000 条分页获取七日内所有原始记录，在 JS 去重；切换类目不再请求 | 1 次 Netlify Function；1 次 Supabase RPC 只返回去重后的类目、子类目、姓名；页面切换类目仍不再请求。响应 no-store，后续读取实时查询 |
| 批量提交 | 1 次函数、1 次 INSERT，每个姓名独立保存 | 不变；提交后的新公开 GET 读取最新数据库内容 |

| 后台姓名搜索 | 连续 5 次输入可触发 5 次函数请求 | 300 ms 防抖；本地 Chrome 快速输入 5 次只触发 1 次。切换类目会取消旧搜索 |
| 后台分页/编辑/删除/导出 | 每次先校验身份；精确计数支持分页；导出原始行含重复姓名 | 身份校验、计数、原始行导出和每 100 条批量删除保留。空姓名筛选不再传 `ilike %%`；清理日志仅取实际显示的 12 条，而非 90 条 |
| 北京时间每日清理 | 每日 UTC 16:00 一个函数调用；数据库 RPC 删除早于北京七日边界的行 | 保留一次原子 RPC；公开查询自身仍按同一边界筛选，即使定时清理延迟也不会显示过期行 |

## 同数据、同脚本的 Supabase 查询测量

命令：`node scripts/benchmark-records.mjs`。在本地 PGlite / PostgreSQL 引擎中，对每组数据重复 5 次，下面是请求总耗时中位数。字节是数据库返回 JSON 的编码长度；SQL 时间来自 `EXPLAIN (ANALYZE, BUFFERS)`。旧 SQL 时间累加了全部分页，新 SQL 为一次 RPC。包含本地运行开销，**不是线上 Supabase 实测**，每次运行数值会略有波动。

| 数据集 | 原始 / 结果行 | 旧→新查询次数 | 旧→新返回字节 | 旧→新本地请求耗时中位数 | 旧→新 SQL 执行时间 | 旧→新共享缓冲命中 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 小数据 | 12 / 8 | 1→1 | 1,441→209 B，少 85.5% | 0.29→0.33 ms | 0.12→0.24 ms | 1→1 |
| 重复姓名多 | 2,400 / 100 | 3→1 | 292,323→2,691 B，少 99.1% | 15.60→5.14 ms | 7.43→4.85 ms | 75→25 |
| 结果超千条 | 2,200 / 2,200 | 3→1 | 274,983→62,691 B，少 77.2% | 13.44→8.48 ms | 6.90→7.16 ms | 69→23 |

小数据的 SQL 计算略增；结果全部不同的场景也略增（6.90→7.16 ms）。因此不能承诺 Supabase 计算积分必然下降。大数据集的往返、函数等待时间及数据库出站更低。现有 `records_submitted_at_idx` 与 `records_visible_dedupe_idx` 已复用；未增索引，避免每次提交额外维护与存储开销。还需用线上等量数据和真实 Postgres 的统计信息验证查询计划。

按每 **1000 次可比名单打开** 归一化：在 2,400 条原始、100 条结果的数据形态下，Netlify Function 仍为 1000 次；Supabase 读取从 3000 次变为 1000 次，数据库到函数的 JSON 约从 292.3 MB 降至 2.69 MB。这不是 Netlify 流量账单的等价换算，且没有计入协议/头部、压缩和其它页面资源。

## 本地合成 API 操作核账

命令：`node scripts/measure-api-paths.mjs`。脚本以同一条示例记录、模拟 Auth 与 Supabase 响应逐项运行真实 Netlify Function 处理器；不访问线上。返回字节只含模拟 Supabase 响应体，不含 HTTP 头、请求体或 TLS；耗时主要反映本地 JS，不能用来估算线上函数计费。

| 单次操作 | Netlify Function | Supabase 上游请求 | 模拟上游响应体 | 说明 |
| --- | ---: | ---: | ---: | --- |
| 打开公开名单 | 1 | 1 | 32 B | 1 条结果；大数据用上一表 |
| 提交 2 个姓名 | 1 | 1 | 0 B | Supabase 写入返回最小响应；实际写入两行 |
| 后台登录 | 1 | 3 | 183 B | Auth 登录、Auth 用户、授权表 |
| 后台名单页 | 1 | 3 | 280 B | Auth 用户、授权表、分页及计数 |
| 后台编辑 / 删除 | 各 1 | 各 3 | 各 135 B | 写入后前端另请求一次名单页 |
| 后台导出 | 1 | 3 | 280 B | 此例少于 1000 行；大导出按 1000 行分页 |
| 北京时间每日清理 | 1 | 1 | 1 B | 原子 RPC |

普通首页与名单页内部切换类目均为 0 次 Function、0 次 Supabase 请求。上述接口统计已包含必要的身份校验；打开后台页面时还会做一次无 Cookie 的会话探测，返回 401，不访问 Supabase。手动登录后显示名单的完整冷页面路径为原先约 6 次 Function / 14 次上游请求，现为约 3 次 Function / 6 次上游请求，其中包含这一次会话探测。账户和日志滚动进入视口时各另发 1 次受保护请求。

## 图片与浏览器缓存测量

原图及压缩图都是 **1672×941 的完整横向构图**；移动端没有预裁剪。原 PNG 1,828,721 B，JPEG 质量 60 为 **196,322 B（0.196 MB）**，文件少 89.3%；相比先前 368,006 B 的 JPEG 候选又少 46.7%。每 1000 次首次图片传输约少 1.63 GB 响应体。本地用 390×844 竖屏、844×390 横屏、1440×900 桌面截图检查了清晰度与布局，截图在 `output/previews/optimized-*.png`。CSS 的 `background-size: cover` 会随视口比例显示图片，源文件仍是完整横图。

一次构建给 CSS、JS、图片生成 SHA-256 内容哈希文件名；各页面引用相同地址。内容改变时文件名改变。构建输出 `_headers`：哈希资源 `public, max-age=31536000, immutable`；HTML `public, max-age=0, must-revalidate`。本地 Chrome 清空缓存后首访请求三种资源，进入填写页 CSS/JS 从缓存读取，重访首页 CSS/JS/图片均从缓存读取。公开名单 API 始终 `no-store`。现有 CSS、JS 单文件 gzip 约 6.6 KB、7.5 KB，拆包/压缩的额外复杂度暂不值得。

## 保留原实现的项目及原因

- 公开名单 CDN / durable 缓存：用户要求完全实时；函数次数不因本轮名单查询优化而下降。
- 每次后台操作的 Auth 与授权表校验：权限安全所需；不把账户信息缓存成可绕过校验的状态。
- 后台精确计数：当前翻页显示准确总数依赖它；未测得它成为主要成本。
- 全量 CSV 与批量删除：导出必须包含重复原始记录，删除需按管理员实际选择 ID；它们不是普通浏览高频路径。
- 每日清理 RPC：已经是每天一次原子操作，改动收益不足以抵消数据一致性风险。
- 新增索引和 JS/CSS 拆包：当前本地计划未证明索引有净收益；脚本与样式压缩后体积较小。
